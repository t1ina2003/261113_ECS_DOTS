05 / THE REAL LESSON

到底哪裡需要 ECS / DOTS？

01 / OOP

幾十隻敵人？
傳統 OOP 就夠了。

每隻敵人都是物件，狀態與行為寫在一起，直覺、容易除錯。少量資料時，額外拆成 ECS 並不一定值得。

enemy.update(player)
02 / ECS

敵人有不同能力？
ECS 幫你拆解組合。

Position、Velocity、Health、AI 可以獨立組合。只有需要移動的 Entity 才交給 MovementSystem，容易擴充功能，但不是效能保證。

MovementSystem(Position, Velocity)
03 / DOD · DOTS-LIKE

數萬隻同時更新？
讓資料連續排列。

只讀取要運算的欄位，用 TypedArray 讓資料存取更規律，減少每個物件的記憶體管理成本；這時可能產生可測量的優勢。

Float32Array → tight update loop
06 / DATA → VIEW

「畫面只是資料的投影」

玩家位置、敵人位置都在模擬引擎中。Canvas 只從資料讀出部分敵人來畫圖。即使畫面只畫 700 隻，系統仍然會對你設定的全部敵人做運算。遊戲邏輯與視覺負擔被刻意分離，這就是這句話最實際的意思。

ENTITIES 完整 N 隻
↓
SYSTEM 更新 N 隻
↓
CANVAS VIEW 只畫最多 700 隻

重要觀念：沒有哪個規模「必須」使用 ECS 或 DOTS。當效能分析顯示模擬資料存取才是瓶頸、資料量很大又需要同類批次運算，才值得嘗試資料導向。此網站的「DOTS 風格」是 JavaScript 的 SoA / TypedArray 範例，並沒有使用 Unity 的 ECS、Burst 或 Jobs。
